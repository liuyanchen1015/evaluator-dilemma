The Evaluator Dilemma ↗

When a self-improving AI system reports that it got better, how do we know the gain is real? For each published system here, we check whether the evaluators that measured the gain can tell better from worse, and whether the gain holds up when we re-check it ourselves, or against the paper's own data when nothing can be rerun.

How to read this registry

Audit protocol

  1. Map every evaluator in the loop. Training signal, selection, stopping, reporting. For each: fixed or co-evolving, what it shares with the policy, what the policy can see, how strongly the loop optimizes for its score, and whether the reporting evaluator is independent of it.
  2. Diagnose each evaluator on items whose quality is known independently, drawn from the loop's own outputs:1 telling good from bad · 2 telling good from better · 3 saturation · 4 rewarding the wrong thing · 5 own score vs. truth · 6 drift and self-preference · 7 what the tests don't cover
  3. Re-check the reported numbers. Use the same evaluation code for start and end, report paired confidence intervals, check the grader against the raw outputs, and re-test the best run on fresh data.
  4. Verdict. State which evaluator measured the reported progress, and whether the diagnostics show that it can be trusted.

Reading an entry

Verdict: outcome of the audit: holds, holds, overstated / partially holds, not reproduced / evaluator fails, not supported (paper's own data).
Evidence in paper: how much evidence the paper itself gives that its gain is real. L0 claim only · L1 independent reporting evaluator and start/end in the same harness · L2 + diagnostics of the in-loop evaluator and checks that individual gains are real · L3 + artifacts public.
In-loop evaluator: fixed (tests, a frozen judge, fixed data), co-evolving (the model or a co-trained model judges itself), hybrid (co-evolving component checked by a fixed one).

EvoLM

not reproducedEvidence in paper L1

EvoLM: Self-Evolving Language Models through Co-Evolved Discriminative Rubrics · arXiv 2605.03871 · 2026

The frozen judge that applies the rubrics cannot tell correct code from wrong code. On the authors' own evaluation setup, the reported gains come from a starting score that was reported too low and from answers being extracted incorrectly. Once these are fixed, no task keeps a significant gain.

AWhat the paper claims

Rubrics that evolve along with the model let it improve itself: +2.2 on average over 11 OLMo3-Adapt benchmarks, led by HumanEval+ (73.7 → 86.2) and MBPP+ (58.4 → 68.5).

Multi-Agent Evolve (MAE)

not reproducedEvidence in paper L1

Multi-Agent Evolve: LLM Self-Improve through Co-evolution · arXiv 2510.23595 · 2025

The model's own judge cannot tell right answers from wrong ones. The script that extracts each final answer often returns a fragment with no answer in it, and the outside judge still marks many of these as correct. When the judge is given the full answer, none of the released checkpoints is significantly better than the starting model (all McNemar p >= 0.068).

One model writes questions, answers them and grades the answers, and improves itself without outside supervision: +4.54% on average across benchmarks.

OpenRSI Index

partially holdsEvidence in paper L0

OpenRSI Index: a benchmark for recursive self-improvement in research agents · GitHub

The hidden test is meant to measure progress from outside the loop, but agents see its score after every submission and adjust to it. By a rough estimate, the gains on isaaclab and ace are much larger than picking the best submission could produce, so they look real. However, the gains on kev and molmo2 cannot be told apart from picking the best, and molmo2's gain came from exploiting the metric. On molmoweb, most of the gain disappears on new data.

AWhat the paper claims

Each task has a hidden test the agent cannot read or change, so its score is meant to measure progress from outside the loop. The agent's result on each task is its best hidden-test score.

BEvaluators in the loop protocol step 1

EvaluatorRoleTypeShares with policyPressureWhat it is
hidden_test_feedbackselectionfixednonedirectEach task's hidden test. The agent cannot read or change it, but sees its score after every submission and uses it to keep, undo or tune changes.
hidden_test_bestreportingfixedhidden_test_feedback—The best hidden-test score over all of the agent's submissions, reported as its result on the task.
Risks to check in this loop
  • The loop optimizes directly for a fixed score, so it can learn to pass without doing what the score is meant to check.
  • The agent can see the evaluator's score, so it can tune against the evaluator.
  • Tasks used to pick versions also count toward the reported result.

EHow this audit was done

What we did · empirical · 2026-10-14
  • Read the released Claude and GPT run logs for 10 tasks, and counted how often the agent's decisions refer to its hidden-test score.
  • Estimated, roughly, how much a score would rise from keeping the best of many submissions when nothing improves, and compared that with each reported gain.
  • Re-tested the starting and final versions of one task, molmoweb, on 3,007 new examples from the same source (about three times the size of the hidden test).
Deviations from the original setup

  • The logs keep only each submission's total score, so we cannot measure how much scores vary between submissions. Using the spread of the scores we do see (0.0027 on kev, 0.042 on molmo2) leads to the same reading for kev and molmo2.
  • We re-tested only one task (molmoweb) on new data.
  • The count of decisions that refer to the hidden score covers only the Claude runs.

R-Zero

evaluator failsEvidence in paper L1

R-Zero: Self-Evolving Reasoning LLM from Zero Data · arXiv 2508.05004 · 2025

We reproduced two rounds with the authors' code. The loop's evaluator, a majority vote over the model's own answers, gets worse within one round: the labels used for training fall from 85% to 71% correct, and for two thirds of round-2 training questions two reference models cannot agree on any answer. MATH accuracy still rises (0.42 → 0.67 → 0.69), almost all of it in round 1. Round 2, with worse labels, adds only +0.02, and the paper itself reports that every model size eventually gets worse with more rounds.

AWhat the paper claims

A question-writer (the Challenger) and a solver (the Solver) start from the same base model and improve together without any outside data; the Solver's accuracy on math and general reasoning benchmarks rises over the rounds.

BEvaluators in the loop protocol step 1

challenger_uncertainty_rewardtraining signalco-evolvingfamilydirectThe Challenger is rewarded most for questions the Solver answers consistently about half the time, with a penalty for repeating similar questions.
consistency_band_filterselectionco-evolvingweightsfilterOnly questions where 30-80% of the Solver's answers agree are kept; proofs and a few other question types are dropped.
fixed_step_checkpointstoppingfixednonenoneThe Challenger stops at step 5 and the Solver at step 15; no evaluator decides when to stop.
math_and_general_benchmarksreportingfixed——Math benchmarks (AMC, Minerva, MATH-500, GSM8K, Olympiad, AIME), graded by answer matching with a GPT-4o recheck, and general reasoning benchmarks (MMLU-Pro, SuperGPQA, BBEH).
Risks to check in this loop
  • The grader is the model being improved (or an earlier version of it), so it may miss the same mistakes the model makes.
  • The grader is trained alongside the model, so it grows less independent each round.
  • The loop deliberately picks the items the evaluator is least sure about.

Double Ratchet (Who Grades the Grader?)

not supported (paper's own data)Evidence in paper L2

Who Grades the Grader? Co-Evolving Evaluation Metrics and Skills for Self-Improving LLM Agents · arXiv 2607.12790 · 2026

The grader evolves together with a skill loop and is anchored on ten labeled examples. We could not rerun anything, because no run data is released. The paper's numbers are fine, but by its own tables the agent improves just as much with a grader that has collapsed and no longer checks anything, so the gain cannot be credited to the evolved grader. By the end of a run, the evolved grader is also no more accurate than the plain LLM judge it contains (both about 0.55). The paper does show that the ten examples keep the grader from collapsing, and it notes itself that a higher task score does not prove a grader is good.

AWhat the paper claims

A grading metric evolved from ten labeled examples is valid (+0.21 agreement with hidden ground truth on MBPP+, ahead of the plain LLM judge it contains), and when it evolves together with a skill loop, the agent gets 88-110% of the gain that ground truth or a hand-written rubric would give.

BEvaluators in the loop protocol step 1

EvaluatorRoleTypeShares with policyPressureWhat it is
evolved_metrictraining signalhybridweightsdirectThe grader for training attempts: several small checks combined, one of which asks an LLM judge (the same model as the agent). When an attempt fails, the failure message is used to write new skills.
skill_critictraining signalfixedweightsfilterAn LLM critic (the same model as the agent) reads every training attempt, and its comments are also used to write skills. It keeps working even in the runs where the grader has collapsed.
ten_item_anchorselectionfixednonefilterTen labeled examples. When the grader is changed, each candidate version is kept or dropped by how well it agrees with these ten.
locked_set_rollbackstoppingfixednonefilterIf the score on the held-out tasks stays 0.10 below the best for five rounds, the skill library is reset to the best round. These are the same tasks the paper reports on. This happened 0-2 times per run, and is turned off in the runs where the grader collapses.
locked_task_scoresreportingfixedlocked_set_rollback—Unit tests, the official execution check or a hand-written rubric on 40-48 held-out tasks, three seeds. The headline figures use the best round on these tasks.
independent_final_judgereportingfixed——Opus 4.8 compares the baseline report with the evolved one, pair by pair. Its rubric for this task was written after reading the reasons a general-purpose judge gave.
Risks to check in this loop
  • The grader is the model being improved (or an earlier version of it), so it may miss the same mistakes the model makes.
  • The agent can see the evaluator's feedback, so it can tune against the evaluator.
  • The checkpoint is chosen on the reported tasks, so the result is optimistic.

Appendix: do our diagnostics measure what they claim? A check on loops with known truth

We ran our own simulated self-improvement loops with Qwen2.5-7B (iterated DPO, 4 rounds, 2 seeds) and kept every round's answers, the scores the loop's evaluator gave them, and the scores of a separate reward model that the loop never sees. That hidden reward model is the truth here, measured in standard deviations of the starting model's scores. D1 and D2 are how often the evaluator picks the truly better of two answers to the same prompt, counting only pairs whose true scores differ by at least 0.25 standard deviations; D2 counts only pairs where both answers score above the starting model's average.

fixed: the hidden reward model, with scores capped at the starting model's average, so it cannot tell apart answers above that level. co-evolving: the model judges its own answers. hybrid: half the model's own judge, half the capped reward model.

What the diagnostics show
  • D2 catches the fixed evaluator's ceiling exactly. Its D1 looks good, but among answers above the ceiling it does no better than chance (0.50). And in the rounds where true quality is higher, more answers get the same top score (D3 0.71-0.72, against 0.52-0.55 in the other rounds).
  • The self-judge is weak throughout (D1 about 0.63), and it keeps saying the answers are better than round 1's whether true quality goes up or down (D5).
  • Among the best answers, the hybrid is no better than the self-judge alone (D2 0.56–0.60 against 0.57–0.60): above the cap, the capped half adds nothing.
  • D6 was measured separately, by having every round's judge score the same fixed set of answers, so changes come from the judge alone. The self-judge gets worse round by round, 0.668 → 0.632 (-0.037 [-0.062, -0.012]), and it does not favor its own round's answers.
Caveats
  • True quality per round varies a lot between the two seeds (the 95% CI over prompts is about ±0.1, but in the same round the two seeds can differ by up to 2 standard deviations), so we only state what holds for both seeds.
